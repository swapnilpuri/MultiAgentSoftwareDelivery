# UI-01 shared shell functional design

**DRAFT — foundation v0.1.** Covers WF-004/006 and shared controls across WF-002/005/007–014; it is not the complete specification of all 14 pages.

## Scope and classification

**Existing** means observed source/contract behavior. **UI-only** means proposed presentation/interaction using existing APIs. **API reuse** means existing authorized calls. **Additive API / backend** means a gap requiring a separate approved contract/service change. **Future** means unavailable. **Human decision** marks an unresolved product choice. No new service, UI framework or replacement state library is proposed.

Retain Angular standalone/lazy components, existing Auth, ProjectContext, WorkspaceApi, RequirementsApi and OperationsTracker. Proposed presentation components: ApplicationShell, Header, Sidebar, ProjectSelector, UserMenu, BackgroundOperationsDrawer, Breadcrumbs, ThemePreference and UnavailableView. Components render state and emit intent; services retain session/context/operation ownership. These names describe roles, not files already implemented. Detailed state/architecture and API specifications follow foundation review.

## Control contract

Common rule C0 applies to every row: authenticated shell requires a valid session; Project Service enforces ownership/tenant permissions. Hiding or disabling a control never grants or replaces authorization. 401 invokes session recovery; 403 is permission refusal, not automatically session expiry. Request failure must not mutate context or fabricate success. Loading/empty/error states below are additional to C0. N/A is explicit when a state does not apply to a local action.

## State, safety and persistence

Server: session, authorization, project metadata, studio operations and decisions are authoritative. URL: active project and deep-link child IDs. ProjectContext: per-tab remembered project ID with authorized reload, existing request-version protection and identity reset. OperationsTracker: followed records in session storage with server revalidation; it is not an account-wide activity database. Preserve current recovery/idempotency records; do not clear an uncertain-start key to simplify navigation. Theme/collapse are local nonsecret preferences; authentication credentials never belong in browser storage. Do not expand storage of project content or form drafts as an incidental shell change.

Selector switch is a coordinated intent: guard → validate target → successful navigation → committed context. Design must account for existing components selecting context during route activation; final implementation should prevent transient mixed-project rendering and restore old context if navigation fails. On direct unauthorized route, show safe error/Projects choice without revealing foreign metadata. Preserve read-only behavior of archived projects and current mutation restrictions; do not globally reinterpret archive semantics here.

Expiry hides private content behind recovery UI and pauses authenticated polling until reauthentication. Preserve only existing permitted in-memory/recovery state; cross-identity return clears user-scoped state. No guarantee of surviving a full authentication redirect with an unsaved form is made; later page design must explicitly specify draft handling before promising it. A server failure alone must not clear identity or project data as if sign-out succeeded.

## Operations and API boundaries

Reuse current `/auth/config`, `/auth/session`, `/auth/logout`, `/projects`, `/projects/:id`, `/models`, project activity and Requirements/Architecture session operation endpoints through existing adapters. Cancel/retry permissions are supplied by the server and existing studio validation. Existing project data has active/archived status, not mockup milestone progress.

API/backend gaps, not shell restyling: authoritative cross-project activity/pagination; durable Discovery operations; measured progress/log contracts; queue/wait/resume; account profile/security edits; notification inbox; global search; aggregate dashboard lifecycle/agent/repository metrics. These require explicit scope and additive versioned contracts before backend/web dependencies. No new microservice is justified by UI-01. Project/model settings must not become permission or secret configuration changes during this design task.

## Foundation journeys and acceptance evidence

J01: Existing configured sign-in → Home → authorized project → Dashboard → existing studio; one session, backed context and legacy routes preserved (SH01–07/13/16).

J02: While A has a durable studio run, switch to B, open drawer, return to A's session; read server state without creating/cancelling a run (SH03/08–12). Run navigation/reload checks must use a deliberately slow deterministic operation; completed-before-navigation evidence is insufficient.

J03: Open a deep link to B while A is remembered; authorize B, display B consistently; deny stale/foreign ID safely (SH03/07). Repeat with slow out-of-order responses and identity change.

J04: Expiry during read or uncertain mutation → recovery → safe same-identity return → reconcile prior outcome before any retry (SH11/15–17). Discovery disconnect remains an explicit limitation, not a durable-run acceptance pass.

J05: Collapse, keyboard navigate, resize to mobile, open/close drawer and change theme; controls remain accessible without stale focus or data loss (SH02/06/08/14 and V01–07).

Proposed later Playwright checks: legacy deep-link regression, guard refusal, project races, first-time versus API-error rendering, operation cancellation race, offline recovery, cross-identity isolation, config-driven OIDC/password views, safe return rejection, accessible menu focus and screenshots at 320/768/1280/1600 in both themes. Full per-page matrix, fixtures, screenshot thresholds and browser coverage remain F5 work. No browser/UI test has been executed for these proposals.
